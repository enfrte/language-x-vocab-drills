learn-language-x — a TypeScript tutorial

How this app's classes and folders came to be — written for someone new to TypeScript. Follow it top to bottom; every concept is shown with the real code from this project. For the full per-method reference see docs/architecture.html.

1. The idea, in one picture

The app memorises vocabulary: it shows a batch of 5 new words, quizzes you in both directions (word → English, English → word), and promotes the batch to “learned”. All of that is business logic. The buttons and colours are the frontend.

We keep business logic in pure TypeScript (no framework, no DOM) so the UI can be swapped — React today, Solid or Alpine tomorrow — without touching a single core line:

3. TypeScript in 10 minutes (the features this project actually uses)

3.1 Type annotations — telling the compiler what a value is

A variable can just say its type. The compiler then rejects assignments that don't match:

let count: number = 0
let name: string = 'nouns'

3.2 Interfaces — describing shapes of data

An interface is a checklist an object must satisfy. Our central data record is src/domain/types.ts

export interface Entry {
  id: number          // positional index in the .jsonl dataset (stable key!)
  xx: string          // the word in the language being learned ("" in code = LANGUAGE.code)
  grammar: string     // part of speech, e.g. "noun"
  meanings: string[]  // English meanings
}

Anywhere a function promises Entry, it only promises to return those four fields. Interfaces do not exist at runtime — they're compile-time documentation the compiler checks.

3.3 Type unions — small, closed lists of possibilities

A value that is one of a fixed set is a union type. This replacement for string-typos means the compiler catches 'xx→en' or 'EN-XX' mistakes instead of your users finding them:

export type QuestionDirection = 'xx-en' | 'en-xx'

3.4 Classes — state plus the functions that protect it

A class bundles data (fields) with behaviour (methods). Members can be:

  • private — visible only inside the class (the outside can't break invariants),
  • readonly — can't be reassigned after construction,
  • get …() — a getter: reads like a field, runs like a method.
export class MultipleChoiceQuestion {
  readonly correct: string          // set once in the constructor
  private chosen: string | null = null

  get answered(): boolean {         // callers read question.answered
    return this.chosen !== null
  }

  answer(option: string): boolean | null {
    if (this.chosen !== null) return null   // first pick wins
    this.chosen = option
    this.right = option === this.correct
    return this.right
  }
}

3.5 Static members — functions that belong to the class, not an instance

Dictionary.toIds(entries) needs no particular dictionary instance, so it is static — you call it on the class, like Math.max.

3.6 Generics — algorithms that work for any type

shuffle shuffles any array without caring about its element type: <T> declares "some type, decided by the caller"

export function shuffle<T>(items: readonly T[]): T[] { … }

shuffle(['a','b','c'])       // T = string
shuffle([{id:1},{id:2}])     // T = { id: number }

3.7 async / Promise — steps that take time

Reading IndexedDB is asynchronous. async functions return a Promise; await pauses (only inside async) until the value arrives. Sessions persist after every meaningful event, so a page reload mid-batch resumes cleanly.

3.8 Dependency inversion — depend on an interface

Domain classes need to save progress but must not know about Dexie/IndexedDB. They take a ProgressStore interface in their constructor; the real implementation is injected from outside (tests inject an in-memory one):

export class LearnSession {
  private readonly store: ProgressStore
  constructor(topicId: string, dictionary: Dictionary, store: ProgressStore) { … }
}

4. The layers in build order

flowchart LR CFG["1 config.ts"] --> TY["2 domain/types.ts"] --> DICT["3 Dictionary"] --> QP["4 MultipleChoiceQuestion"] QP --> LS["5 LearnSession"] --> RS["6 RecallSession"] --> ST["7 storage (StoreKeys → interface → Dexie)"] ST --> FAC["8 LearnXApp facade"] --> UI["9 demo-ui + console"]
  1. config.ts — one constant object naming the language ('xx'), its display name, and the teaching language 'en'. Every other "Māori" reference in either docs, data or code flows from here — this file is what makes the app learn-language-x: swap the values and the datasets, and nothing else changes.
  2. domain/types.ts — new-file-friendly shared vocabulary (Entry, phases, QuestionView…).
  3. Dictionary — parses one topic's .jsonl text into Entry[] (words, frequency order) plus by-grammar groups, because multiple-choice decoys feel more plausible when the distractor is the same word class. Also holds lookups (word(id)), progress maths (learnedStats), selection (pickUnseen) and decoys (distractors).
  4. MultipleChoiceQuestion — one question, immutable prompt/options plus the pick state machine (first pick wins). Renderers never touch this class; they receive a plain QuestionView snapshot. Giving a frontend plain data instead of live objects is what makes frameworks interchangeable.
  5. LearnSession — the learn loop for ONE topic: resume-or-pick batch → review phase → quiz round 'xx-en' → round 'en-xx' → completeBatch merges ids into learned, clears in-progress, picks the next batch. Wrong answers re-queue at the end of the round's queue.
  6. RecallSession — the recall loop: learned ids sorted ascending (frequency order) as the canonical origin, a live queue that reshuffles (right → tail of queue; wrong → +5 positions), a resumable save index pointing into the origin, and dangling-id tolerance.
  7. storage — StoreKeys (naming: learned:<topic> …), ProgressStore (a 6-method contract) and DexieProgressStore (Dexie 4 = IndexedDB).
  8. LearnXApp — the facade: owns sessions per topic, exposes ~10 boring commands (openLearn, answer, advance, toggleTheme, snapshotAll…), and fans out notify() to subscribers. This one class is the entire surface a frontend needs.
  9. demo-ui — 100 lines of vanilla TS: render app state to innerHTML, hash-based routing, one delegated click handler. It is deliberately thin: the tutorial's goal is that you can delete it and write <App/> in a framework you like.

5. Plugging in your own frontend

The facade is the contract: call commands, receive notify(), read state, never reach deeper. Two ways to drive it:

5.1 The browser console (no build step!)

The demo entry point calls installConsoleApi(), which freezes a window.lex object. Play:

lex.config                     // { code:'xx', name:'Māori', source:'en' }
await lex.app.snapshotAll()    // [{ topic, stats:{count,total,percent} }, …]
lex.app.dictionary('verbs')    // the Dictionary instance (memoized)
await lex.app.openLearn('nouns')
lex.app.sessionLearn.questionView   // the on-screen question, plain data
lex.app.answer('house')
await lex.app.advance()
await lex.app.resetAll()

5.2 React (sketch)

import { app } from './src/app'

function App() {
  const [, force] = useReducer((n) => n + 1, 0)
  useEffect(() => app.subscribe(force), [])           // facade notify → re-render
  if (app.view === 'landing') return <Landing />
  if (app.view === 'learn')   return <LearnView session={app.sessionLearn} /> // QuestionView as props
  return <RecallView session={app.sessionRecall} />
}

Solid/Alpine versions follow the same shape — they read state in their reactive computations and call the same commands. Nothing in the core mentions a framework, which is the definition of frontend-agnostic here.

Testability bonus: because sessions take a ProgressStore interface and a Dictionary takes raw text, you can construct the whole app in vitest with an in-memory store — see tests/domain.test.ts. FOUC-free theming is another perk: the facade reads localStorage synchronously, so the demo applies the dark class before the first render.

6. Swapping datasets / making it learn-language-y

  1. Drop new fr-en-dic-* files into src/data/datasets/. Each line must look like: {"fr":"bonjour","gr":"noun","en":["hello"]} — the word key MUST match LANGUAGE.code.
  2. Update REGISTRATIONS in src/data/registry.ts (id, label, file, bundled ?raw import).
  3. Change LANGUAGE in src/config.ts (code: 'fr', name: 'French').

Prompts, store keys, deep links, and the whole demo UI derive from those values — nothing in domain/ or storage/ mentions a specific language.

Two quirks intentionally preserved from the original learn-maori:
1. pickUnseen returns the next N entries in frequency order, not shuffled (the original commented out its shuffle).
2. A RecallSession queue never becomes empty through normal answering (a right answer always re-inserts the word at the tail) — Recall is an endless practice loop, resumable via the saved index. Both are documented in docs/architecture.html.

7. Short exercises to make it stick

  1. Add a strength field to MultipleChoiceQuestion as a union 'weak' | 'strong' derived from wasRight.
  2. Create a MissingLetterQuestion class implementing the same shape as MultipleChoiceQuestion, and swap one Learn round to use it.
  3. Implement a LocalStorageProgressStore and unit-test it against the same suite as the Dexie one (inject it into new LearnXApp(store)).
  4. Put a 3-button counter on the landing page in Alpine — five lines of HTML — driven only by lex.app.
